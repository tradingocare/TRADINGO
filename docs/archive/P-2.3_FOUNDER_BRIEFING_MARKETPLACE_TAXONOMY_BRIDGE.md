# TRADINGO® — Founder Briefing
## Phase P-2.3 — Marketplace Taxonomy Bridge

Date: 2026-07-04
Prepared by: Engineering (for Founder review)

---

1) Executive Summary

Purpose: implement the Marketplace Taxonomy Bridge to reliably map existing marketplace categories and free-text service/product labels to the new Master Catalog taxonomy so frontend experiences and backend integrations can use canonical catalog categories without changing the Master Catalog or running migrations.

Objective: prepare a minimal, reversible, non-invasive implementation that provides deterministic resolution (old→catalog, catalog→old), mapping coverage metrics, and a unified-search enrichment layer. No database schema or Prisma changes will be made in this phase. Implementation will be limited to API/service and frontend wiring using existing models and read-only queries.

Governance: per Founder-approved SSOT, nothing will execute (migrations, deployments, seeds) until Founder explicitly issues START. This briefing defines the gated scope and success criteria for that START.

---

2) Scope of Implementation (what we will do in P-2.3)

- Implement deterministic mapping logic and resolution endpoints in the Marketplace Catalog Bridge service layer (read-only against existing DB). Use existing `marketplace-catalog-bridge.service.ts` and the already-added controller endpoints.
- Add mapping coverage calculations and admin endpoints (read-only aggregation) to report percent-mapped, unmapped-high-volume buckets, and confidence metrics.
- Provide unified-search enrichment API to return combined results (old marketplace + catalog matches) for a query set (no index changes). This feeds frontend enrichment and discovery components.
- Wire frontend API clients and hooks to call the new bridge endpoints (read-only displays and badges). Update UI to show mapping status and catalog badges where applicable.
- Add thorough logging and feature-flag gating so behavior can be toggled off immediately (no runtime DB changes required).
 - Add thorough logging so behavior can be observed and traced (no runtime DB changes required).

Scope constraints (explicit):
- Do NOT change Prisma schema, migrations, or database structure.
- Do NOT add or modify seed/migration scripts.
- Do NOT run migrations, tests, or deployments as part of this phase.
- Do NOT modify frozen modules (GOCASH, AI Gateway, Auth, Notifications, Master Catalog models).

Deliverables for P-2.3 (pre-execution artifacts):
- Code changes limited to: API controllers, services, DTOs, logger/tracing, frontend API wrappers and hooks, UI presentation bits (badges, status indicators).
- A pre-execution checklist and smoke-test plan (document only) to be executed after Founder START.

5) Expected Marketplace behavior (user-facing)

- Search and category pages will show catalog-enrichment badges for items/services that map to the Master Catalog.
- Category discovery and service lists will surface a “Mapped to Catalog” indicator and (optional) catalog category link without altering existing marketplace slugs/URLs.
- Admin coverage dashboard will show mapping coverage percentages by category, high-volume unmapped clusters, and allow CSV export of unmapped IDs for manual curation (export only; NO writes).
- No change to purchasing, checkout, or existing business workflows.

---

6) Expected Master Catalog behavior (backend/canonical)

- The Master Catalog remains authoritative and unchanged. P-2.3 only reads catalog models via existing Prisma client and uses them as targets for mapping.
- No master catalog writes, no new fields, and no index changes.
- Mapping logic will prefer deterministic slug/label matches, fall back to similarity heuristics (configurable), and expose confidence scores in API responses.

7) Rollback strategy

Principles: all changes must be reversible by code revert and service restart; the bridge must be removable by reverting code and restarting services.

Rollback steps (high-level):
1. Revert code in the development branch to the pre-P-2.3 commit and rebuild/restart the development service.
2. If UI changes were applied in development, revert frontend to prior commit and rebuild.
3. No DB rollback required because no migrations/seeds are applied.
4. No DB rollback required because no migrations/seeds are applied.

Emergency rollback: if a regression is detected, disable bridge via feature flag and create a hotfix branch to revert only the changed files listed above.

---

8) Risks

- Data mismatch risk: mappings derived from heuristics can be incorrect and create misleading catalog badges. Mitigation: expose confidence scores, show “suggested” label on low-confidence mappings, provide easy feedback loop (export CSV of unmapped or low-confidence items for manual curation).
- Coverage gaps: large tail of low-frequency categories may remain unmapped initially. Mitigation: coverage dashboard and prioritized curation list by volume.
- Performance impact: enrichment lookups could add latency to search endpoints if called synchronously. Mitigation: ensure the bridge uses batched queries, caching (in-memory short TTL), and async enrichment where acceptable; add rate limits and observability.
- Unexpected coupling: other modules might implicitly rely on marketplace internal category IDs. Mitigation: keep bridge behavior purely additive and opt-in behind feature flag and gateway wiring; do not alter existing IDs or flows.
- Security/exposure: exposing mappings may reveal internal taxonomy. Mitigation: restrict admin endpoints with existing JwtAuthGuard + RolesGuard; public endpoints only expose non-sensitive mapping metadata.

Residual risk acceptance: low-to-medium risk is acceptable for development rollout with strong monitoring and ability to revert code.

Pre-execution (must be satisfied before START):
- Founder approval of this briefing and the pre-execution checklist.

- No critical or high-severity errors observed during development verification; latency impact measured and acceptable for development environment.
- Admin coverage dashboard shows prioritized unmapped list and allows export for curation.
- Frontend displays mapping badges correctly in development without visual regressions.
