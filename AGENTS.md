## MASTER VISUAL ENGINEERING & ACCEPTANCE PROTOCOL (FOUNDER LOCKED — 2026-08-14)
PERMANENT WORKFLOW RULE for ALL future TRADINGO UI/LAYOUT tasks. Objective is NOT merely technical validity — it is visual correctness, spatial balance, readability, responsiveness, consistency, production-safety, and faithfulness to Founder-approved screenshots/design intent.

### Core Principle
NEVER equate "0px horizontal overflow" / "build passed" / "TypeScript passed" with "visual design is correct." Technical correctness and visual correctness are SEPARATE acceptance criteria. A page may have 0px overflow, valid HTML/CSS, successful build — and STILL be visually wrong (content too narrow, typography too small, sections too tall, excessive empty space, inconsistent spacing rhythm, too many text lines, weak hierarchy, compressed screenshots, poor responsive composition). Such a result MUST NOT be reported as "PASS."

### Founder Screenshot = First-Class Requirement
Treat Founder screenshots as visual acceptance evidence. Do NOT reinterpret the problem as a generic technical issue. Extract from the screenshot: section/card/content width, relative spacing, typography scale, line count, visual density, empty space, alignment, hierarchy, section rhythm. Compare the implementation against those observations. If the screenshot shows "11 lines should become ~8 lines", test line count and content width. Do NOT say "max-width is intentional" without proving the existing width matches the Founder-approved visual result.

### Mandatory Phases (all required)
- **Phase 0 — Build Identity Check**: identify git revision, working-tree state, files with intended changes, current Next.js server/process; confirm localhost serves the CURRENT working tree (no stale `.next`); rebuild/restart locally if necessary; record build timestamp/hash. A visual audit on a stale build is INVALID.
- **Phase 1 — Baseline Capture**: before modifying, capture real-Chromium baseline at relevant viewports: screenshot, viewport w/h, deviceScaleFactor, CSS viewport, zoom, URL, scroll position, section/content bounding boxes, heading+paragraph font sizes, line counts, section heights, horizontal/vertical padding, inter-section gaps. Use COMPUTED browser geometry, not source-code class names.
- **Phase 2 — DOM/CSS Chain Analysis**: trace SECTION → outer container → inner container → content wrapper → heading → paragraph → CTA. Identify where width/height is constrained. Measure availableWidth, contentWidth, contentUtilizationPercent (e.g., 1180 available / 720 content / 61% — must be explained). Inspect max-width, width, min-width, flex-basis, grid columns, padding, margin, nested wrappers, typography, line-height, `br`, nowrap, word-break, clamp, min-height, fixed height, flex centering, absolute positioning, transforms.
- **Phase 3 — Root Cause**: every issue must have a specific root cause. Acceptable: "Paragraph is limited to 720px by nested max-w-2xl inside a 1180px content container, producing 11 lines at 375px and unnecessary section height." NOT acceptable: "Spacing could be improved." / "Responsive issue." / "Looks okay now."
- **Phase 4 — Implementation**: fix the root cause. NEVER use cosmetic hacks: arbitrary transforms/scaling/zoom, overflow-hidden to hide content, overflow-x-hidden, line-clamp to shorten content, content clipping, negative margins unless proven intentional, arbitrary fixed heights/widths. Prefer correct container width, responsive padding, typography, flex/grid behavior, content-driven height, natural wrapping, shared primitives when proven safe.
- **Phase 5 — Before/After Proof**: REBUILD, capture new screenshots, re-measure same geometry, provide BEFORE → AFTER table (content width, utilization %, heading/paragraph line counts, section height, top/bottom gap). If the screenshot did NOT materially improve, the task is NOT complete.
- **Phase 6 — Visual Acceptance**: for every Founder-reported issue ask "Can the Founder look at the new screenshot and clearly see the problem is fixed?" If NO → DO NOT report PASS; return to root-cause analysis.
- **Phase 7 — Multi-Breakpoint Testing**: test ONLY after the visual result is correct. Desktop: 1280/1440/1920. Tablet: 768/820/1024. Mobile: 320/360/375/390/414/480. "0px overflow at all widths" is NOT the only acceptance condition — also verify readability, line count, visual density, card height, spacing, alignment, hierarchy.
- **Phase 8 — Shared Component Impact**: if a component is shared: count usages, determine affected pages, verify representative pages BEFORE and AFTER changing it. Do not claim global safety from testing only one page.
- **Phase 9 — Screenshot Comparison**: when Founder provides a reference screenshot, compare at same viewport/zoom/scroll position/comparable device scale; create before/after overlay/difference analysis if possible; report what materially changed.
- **Phase 10 — Technical Validation**: ONLY after visual acceptance: TypeScript, ESLint, tests, build. Technical green is the FINAL safety layer, not the definition of visual success.
- **Phase 11 — Final Report**: every visual task report MUST contain: A. Founder-reported problem, B. baseline screenshot evidence, C. root cause, D. exact implementation, E. before→after visual measurements, F. before→after screenshot comparison, G. responsive verification, H. shared-component impact, I. TypeScript, J. ESLint, K. tests, L. build, M. remaining issues, N. explicit "VISUAL ACCEPTANCE: PASS" — only if the Founder-reported visual issue is demonstrably resolved.

### Stop Conditions
STOP and report instead of pretending success if: current build is stale; screenshot cannot be captured; browser rendering cannot be verified; reference screenshot cannot be compared; visual result remains materially unchanged; root cause is uncertain; a shared change introduces unexplained regression; production state cannot be verified.

### Source Control / Deployment
Default workflow: AUDIT → BASELINE → ROOT CAUSE → IMPLEMENT → REBUILD → SCREENSHOT → BEFORE/AFTER → RESPONSIVE VERIFY → TECHNICAL VALIDATION → FOUNDER REVIEW → DEPLOY. Do NOT deploy merely because build/tests pass. Do NOT commit unreviewed visual changes.

### Final Rule
NEVER tell the Founder "FIXED" / "COMPLETE" / "PASS" / "READY" based only on build success, TypeScript success, ESLint success, or overflow = 0. A visual task is complete ONLY when: THE SCREENSHOT LOOKS RIGHT AND THE MEASUREMENTS SUPPORT IT AND THE TECHNICAL CHECKS PASS.

## Key Decisions
- `Restrict` for critical-chain FK relations (financial, escrow, dispute, compliance)
- `SetNull` for optional/soft-link FK relations (Payment.order, FileScan.company)
- `NoAction` for archival analytics (PlanHistory)
- `Cascade` only for POD/execution records (ManualPaymentProof→Payment, DisputeProcessorExecution→Dispute)
- `normalizeStatus()` centralized in status-badge.tsx
- Canonical role representation is uppercase (`ADMIN`, `SUPER_ADMIN`, `SELLER`, `BUYER`)
- Pagination format: `{ data, meta: { total, page, limit, totalPages, hasNext, hasPrevious } }`
- Global ValidationPipe error: `{ statusCode: 400, message: string[], error: "Validation Error", timestamp }`
- `findQuotes` in SmartRfqService uses Prisma directly (not QuoteService) to avoid circular module deps
- Seller controllers use typed DTOs (no more `@Body() body: any`)
- `/smart-rfq/:id/quotes` shortcut instead of `companies/:companyId/rfq/:rfqId/quotes` to avoid company ID resolution on frontend
- **Single AI Workspace page, not 5 separate pages**: Dashboard, catalog quality, bulk processing all consolidated into one page with cards/tables
- **CopilotPanel as reusable component**: Embedded in product edit page sidebar, wired to existing use-ai hooks
- **No AI credits enforcement in this phase**: Membership system has no credit fields yet; CopilotPanel shows placeholder UI, no hardcoded limits
- **Mixed pattern**: Product edit page uses raw axios for form, CopilotPanel uses React Query hooks alongside it
- **SuggestionCard shows preview before accept**: Accept calls acceptSuggestion mutation, Edit allows JSON override before applying
- **AiNegotiationService lives inside Smart Negotiation module** — no new module, extends existing `smart-negotiation/` directory
- **TaskType.NEGOTIATION already exists** (costs 20 credits via CREDIT_COSTS) — all 12 AI features reuse this existing type with different `action` fields
- **AI suggestions are ephemeral** — no new Prisma model; all suggestions generated on-demand via AI Gateway
- **Seller + Buyer pages both get identical copilot integration** — component auto-detects role and shows relevant buttons
- **Wizard AI uses inline buttons per step, not sidebar** — the wizard has no productId until creation, so AI actions fill form fields directly instead of using accept/reject pattern
- **Single TaskType for multi-action AI modules** — CRM_ANALYSIS (12 actions), FINANCE_ANALYSIS (10 actions), SEARCH_ANALYSIS (11 actions) all use one TaskType with different `action` fields in payload
- **AI modules extend existing domain modules** — AiFinanceService/Controller inside FinanceModule, AiSearchService/Controller inside TradfindModule, never standalone AI modules
- **Search AI is insight-only** — never modifies search results or ranking algorithm directly; provides re-ranking criteria/enrichment for frontend to apply
- **Cost structure**: FINANCE_ANALYSIS = 10 credits (complex analysis), SEARCH_ANALYSIS = 5 credits (lightweight text generation)
